## 1. 范围与原则

- 输入仅分为 `FIRST_SURGERY`（首台手术信息）、`CANCELLATION`（手术室退单信息）、`SURGERY_DETAIL`（手术明细查询）三类固定 Excel 格式。Word 指标说明不再是新会话的输入或计算依据。DOCX 报告输出可以保留。
- 查询默认且始终只访问当前对话的数据。每次补传产生新的 `data_revision`；旧查询与报告固定原 revision，不被后续上传改写。
- Excel 原件仍放在现有 SHA-256 Blob 目录。SQLite 存来源、可查询字段、质量问题和数据版本。原始行可通过文件哈希、Sheet 与行号找回，不在普通日志中复制患者明细。
- 三类文件保持各自的来源粒度。首台子集与明细不能相加，退单事件不能自动视为已实施手术。跨表关联只使用经验证的业务键和已批准关系。
- 表结构知识库描述字段含义、别名、枚举、查询能力和允许的关联；手动指标库独立保存自然语言定义及经过验证的 SQL 版本。模型可以提出结构化查询计划和供用户查看的 SQL 草稿；应用根据知识库编译参数化 SQL，模型原始 SQL 文本不直接进入执行器。

## 2. 数据库文件和类型约定

沿用 `%LOCALAPPDATA%/DataMind/datamind.sqlite3`、WAL 和现有 `blobs/<sha256>`。现有 `objects`、`jobs`、`events` 保存会话、轮次、运行和队列元数据；新业务行使用专表，避免几十万行 JSON 对象扫描。暂不引入独立数据库服务或向量库。

| 语义 | SQLite 表示 | 规则 |
| --- | --- | --- |
| 住院号、患者 ID、姓名等标识 | `TEXT` | 保留前导零；空字符串归一为 `NULL`；住院号不是手术唯一键 |
| 业务日期 | ISO `YYYY-MM-DD` 的 `TEXT` | 用固定格式解析器校验合法日期；观察到的最早/最晚日期不等于完整覆盖声明 |
| 首台/明细时刻 | 原始 `HH:MM` 的 `TEXT` + 0-1439 的分钟 `INTEGER` | 样例只有时分，没有日期或时区；可比较同日时刻，跨午夜时差须先明确政策 |
| 退单时间 | 本地 ISO 日期时间 `TEXT` | 样例是 Excel datetime，但未携带时区；不能直接转 UTC 或替代“日期”列 |
| 精确数值 | 十进制字符串 `TEXT` 或整数最小单位 | 计算继续采用精确整数/有理数；不用 SQLite `REAL` 保存正式数值 |
| 缺失值 | `NULL` + `data_issue` | 区分原文件为空、无法解析、字段不存在和业务不适用 |
| 行定位 | `sheet_id` + `excel_row` | 指向托管原件；`row_sha256` 用规范化行内容计算，便于核验 |

各时间列保留原始 `HH:MM` 文本与解析出的分钟值。时间字段为空或非法时分钟值为 `NULL`，并写入 `data_issue`。只有完整日期时间或经业务批准的跨日规则才能计算持续时间；当前样例不能仅凭 `23:50` 与 `00:10` 推断相差 20 分钟。

## 3. 来源、版本和业务表

`data_space` 与现有 `session` 对象一对一，由应用事务检查对应会话存在。上传请求先在现有附件/Blob 存储按幂等键登记；完成格式识别后才创建 `STAGING` 的 `data_source`，写入三选一类别、格式版本/hash、解析器版本和入库 Skill ID/版本/hash。`data_source` 保存当前对话归属、原件 SHA-256、入库状态、行数及来源日期范围；`data_sheet` 保存每个 Sheet 的表头位置和表头哈希。`source_fingerprint` 在退单手术室归属确定后，由文件哈希、原始文件名、格式版本/hash、解析器版本、Skill 版本/hash、最终手术室、归属依据及归属策略 hash 规范化计算；此前可为空，相同指纹在当前对话中复用已有 READY 来源。发布 revision 的事务还须按原件 SHA-256 检查来源清单，数据库触发器拒绝同字节文件改名后在同一 revision 重复计数。来源维度更正时创建新来源和新 revision，旧来源及其解析结果保持不变。跨对话可以共享物理 Blob，但保留独立逻辑来源。退单文件缺少“手术室”列；`data_source.origin_operating_unit` 根据文件名语义相似度确定，无法确定时由用户手动选定。`origin_unit_basis` 分别记录 `FILENAME_SEMANTIC` 或 `USER_CONFIRMED`，`origin_unit_evidence_json` 保存匹配或确认依据。

`data_revision` 是不可变来源清单，`data_revision_source` 列出该版本包含的 READY 文件。其复合外键同时检查 revision、父 revision 和 source 的 `session_id`，防止把其他对话的数据加入当前版本。`manifest_sha256` 由按稳定顺序排列的来源 ID、来源指纹、文件哈希、格式版本、解析器版本和 Sheet 哈希规范化计算。新版本只改来源清单，不复制旧业务行。查询开始时固定 revision ID；“当前版本”由同一对话最大的 `revision_no` 决定。READY 来源、Sheet、业务行和已发布 revision 在服务层禁止原地修改；如需更正，建立新来源/版本。数据库外的维护脚本也须遵守这一约束。

三个业务表逐列对应样例表头。完整的 SQL 类型、索引和约束见建表草案，精确列位置见格式合同：

| 表 | 来源列分组 | 存储与查询注意点 |
| --- | --- | --- |
| `first_surgery_row` | 手术日期、手术室、手术间、住院号、患者ID/姓名、手术科室/医生、入室/麻醉开始/手术开始时间、主麻、手术名称、术前诊断 | 14 个源列完整保留；时间为时分，来源已筛出“首台”，但筛选算法与是否为实际已实施仍需业务确认 |
| `cancellation_row` | 序号、日期、住院号、姓名、手术类别、手术间、台次、术者科室/人员、退单时间/人/类别/原因 | 16 个源列完整保留；日期与退单时间分别存储，退单类别的复合值另拆为 `cancellation_tag`，不修改原文 |
| `surgery_detail_row` | 手术日期、手术室/间、住院号、患者姓名/性别/年龄、临床科室、手术/麻醉/切口属性、八个时间节点、诊断及手术团队 | 29 个源列完整保留；没有单独执行状态，以手术开始/结束等字段作为实际手术证据是否足够需确认 |

住院号、患者 ID、姓名都不设全局唯一约束。来源可能重叠、同一住院号可能有多台手术，直接约束会丢失冲突证据。唯一约束只保证同一 Sheet 的 Excel 行号不重复；插入触发器检查业务行表与来源类型一致。按来源/日期/手术室、住院号建立查询索引；住院号索引是检索辅助，不代表批准关联。跨表关系由知识库批准后才能启用。

`data_issue` 记录文件、Sheet、行、列、错误码、严重度和不含明细值的描述。表头或格式版本不匹配会使整份文件失败；个别行字段有问题时保留该行和问题。查询能否继续由指标口径决定，不能静默跳过后宣布完整统计。

### 退单文件识别与手术室归属

退单**文件类型**和所属**手术室**是两个独立判定。三份退单样例的内部标题均为“退单手术信息查询”，第 2 行均为同一组 16 列有序表头，Sheet 名均为 `sheet1`；其中二手、三手文件名没有“退单”二字。因此先校验真实 XLSX 格式、可见 Sheet、标题及 16 列表头的完整顺序，匹配 `CANCELLATION` 格式版本后才入库。文件名不能决定文件类型。退单样例的工作表尺寸元数据错误，解析时需 `reset_dimensions()` 并以实际行流校验上限。当前 `files.classify()` 仅识别通用 `DATA_FILE`，`parse_xlsx()` 的快照没有保留前置标题；新三类导入器需要保留标题并增加固定格式匹配。

退单表没有“手术室”列，只有“手术间”。按 2026-10-16 至 22 日样例，用同期间首台/明细中的 `(手术间, 手术室)` 仅做核对，三份退单的 57 个非空手术间编码全部与文件名“一手/二手/三手”的归属一致：一手退单 122 行归第一手术室、12 行手术间为空；二手 3 行归第二手术室、1 行为空；三手 12 行归第三手术室。编码 `75` 在同一周明细里多数标为第三手术室、另有 1 行标为第一手术室，说明手术间编码不能替代文件名成为默认归属规则；有明显冲突时应提示复核。

将用户所说的“一号/二号/三号手术室”存为受控代码 `OR_1`、`OR_2`、`OR_3`。匹配策略维护“第一/第二/第三手术室”“一手/二手/三手”等文件名别名，限定“退单文件所属手术室”的语境；先去掉扩展名、日期区间、复制/导出等噪声，保留一二三等区分词。唯一的完整别名匹配可以直接接受；其他文件名对三个候选的别名计算语义相似度，只有最高分达到经标注样本校准的阈值且与第二名拉开足够差距才自动归属。不能使用模型自报置信度冒充相似度；当前三份正例不足以校准模糊匹配阈值，发布前需要补充负例与歧义文件名。没有唯一别名命中且语义模型不可用、无命中、多候选或分数接近时，不强制三选一，转用户手动选择。

1. 文件内容通过 `CANCELLATION` 格式校验后，读取原始文件名并运行版本化语义匹配器；输出三个候选分数、最高分与第二名差距、命中别名、策略/模型版本和判定原因。文件名只用于手术室归属，不用于判断它是否为退单文件。
2. 判定唯一且满足已校准的自动接受条件时，将 `origin_operating_unit` 写为 `OR_1/OR_2/OR_3`，`origin_unit_basis=FILENAME_SEMANTIC`，来源可进入 READY。无法确定时进入 `NEEDS_UNIT_CONFIRMATION`，不进入查询 revision；界面让用户在三个手术室中手动选定，保存 `USER_CONFIRMED` 与确认记录后再变为 READY。用户的显式选择可以纠正自动结果，并建立新来源/revision。
3. 可选地用非空“手术间”与已审核字典做冲突审计；它不取代文件名判定。若发现明确的混合手术室或与文件名判定冲突，暂停自动发布并让用户核对整份文件。未知或空手术间本身不阻止文件名自动归属。
4. 手术间为空的 13 行保留空的原始 `operating_room`；文件级手术室确定后，查询通过来源表给这些行归属，同时记录空值行数。不可伪造行内手术间。若未来允许同一文件混合多个手术室，必须改为逐行归属并建立新的格式/存储版本。

`origin_unit_evidence_json` 保留原始/归一化文件名、候选分数、差距、匹配器及别名版本、自动/手动决策原因和手动确认记录；房间编码审计若执行，另记校验字典版本及冲突行数，不包含患者明细。更正归属时新建 `data_source` 与 revision，保留旧版本的归属和查询结果。

## 4. 表结构知识库

表结构知识库的单一维护来源建议为仓库中的版本化 JSON；安装或升级时结构校验、与 SQLite `PRAGMA table_info` 对照并导入 `kb_*` 表，数据库是运行时检索副本。`kb_release.content_sha256` 是规范化 JSON 的哈希。发布后只读；改字段含义、别名或关联时发布新 release，历史运行继续引用旧 release。用户手动维护的指标独立于 `kb_release` 做 CRUD，发布的指标版本引用其生成时的 KB release/hash。

| 表 | 需要维护的知识 |
| --- | --- |
| `kb_release` | 知识库版本、存储结构版本、内容哈希、草稿/发布状态 |
| `kb_active_release` | 唯一生效知识库指针；新导入和新查询按此版本执行，历史 Run 引用旧发布版 |
| `kb_layout` | 三种固定来源的标题标识、表头行、精确列顺序与解析政策；来自版本化格式合同 |
| `kb_entity` | 逻辑实体、物理表、来源类别、单行粒度、描述、默认日期字段 |
| `kb_query_capability` | 动态计划允许的聚合/查询能力、业务粒度、去重政策、结果单位和启停状态；不是手动指标 |
| `kb_field` | 逻辑字段与物理列、类型、单位、空值含义、可用过滤/分组/聚合、敏感级别和值字典；派生字段另存受控访问路径 |
| `kb_relation` + `kb_relation_key` | 允许连接的实体、复合键、基数、未匹配处理、批准证据和启用状态 |
| `kb_term` | 中文术语、缩写及别名到实体或字段的映射；同词多义允许多个候选 |
| `kb_query_example` | 典型问题与期望结构化计划，用于检索辅助和回归测试 |
| `manual_metric` | 手动创建的稳定指标 ID、当前发布版本和软删除状态；已删除指标不再参与新查询 |
| `manual_metric_version` | 不可变发布版本：人工输入的名称/自然语言描述、AI SQL 草稿、本地编译模板、KB 依赖、参数合同、校验回执和审核时间 |

`manual_metric_fts` 与 `kb_search_fts` 是可重建的 FTS5/trigram 派生索引，分别用 BM25 对指标候选和知识库字段/术语候选排序；建表与权重见[BM25 索引合同](contracts/manual-metric-fts-v1.sql)。二字别名先做精确匹配；BM25 top-K 未命中不能直接解释为没有指标，仍须完成候选目录检查。FTS5 不可用时用内存中文 n-gram BM25 回退，执行权限始终由 `manual_metric_version` 与 `kb_*` 正表决定。

知识库不能仅由数据库列名自动生成。已从样例确认的语义边界包括：

- “手术室”是大区域，“手术间”是具体房间；退单文件只有“手术间”，没有可直接使用的大区域列。
- 首台文件是系统输出的首台子集，但未提供产生该子集的筛选规则，也没有计划开始时间列。不能把明细中每天每间最早的一例默认当作同一口径。
- 明细的“手术类型”有择期、急诊及少量其他值；这不是“已实施状态”。“手术开始时间”仅有时分，是否足以证明已实施需业务核验。
- 退单的“日期”和“退单时间”是不同字段；“退单类别”可同时包含多个标签，查询具体类别应走 `cancellation_tag`，而不是对原始文本做模糊 `LIKE`。
- 样例没有共同的手术唯一编号，首台/退单的住院号与明细没有交集。`kb_relation.state` 初始为 `DISABLED`，不能在样例上批准跨表连接。未来若出现稳定键，仍需确认基数、重复导出和多次退单政策。

`kb_field.value_dictionary_json` 只能存业务确认过的枚举政策。样例中观察到的值和频数属于数据画像，不能自动升级为永久合法值字典。

知识库种子逐一列出格式合同中的 14、16、29 个来源字段。导入程序以格式合同的 `column` 为逻辑字段 ID，以 `header` 为原始中文名称，再叠加种子里的含义、过滤操作、分组权限和敏感级别。所有来源列在数据库层允许 `NULL`，故 `kb_field.nullable=1`；具体必填门禁由格式版本另定。`DATE`、`LOCAL_DATETIME`、`INTEGER` 可映射同名知识库类型；`TIME_HHMM` 与 `CSV_TAGS` 的原始列先映射为 `TEXT`，分钟数和标签另作为受控派生字段。未配置过滤/分组操作时权限为空，敏感级别默认 `BUSINESS`，空值含义以来源空白与 `data_issue` 错误码共同解释。未列出的字段、操作或投影默认拒绝。种子中标注为 `PERSONAL` 的字段不得把明细值送给模型；可在本地受控查询，但需要单独定义展示权限。`derivedFields` 不对应 Excel 列：退单标签通过 `cancellation_tag`，已确认的手术室通过 `data_source`；导入 `kb_field` 时必须写入 `physical_table` 和闭合的 `access_path_json`，由编译器选择预定义路径。多标签分组先按退单行和标签去重，同一行的多个不同标签可分别计入各标签，但不能把各标签行数相加当作总退单台次。未确认来源手术室的行不能进入按手术室统计，须返回排除行数和原因。

知识库发布流程校验 59 个来源字段与三张业务表的列名、类型、顺序及敏感级别完全一致；检查派生字段路径、术语目标、`kb_query_capability` 和关系键引用的字段均存在。`kb_relation` 初始为 `DISABLED`，此时基数可以是 `UNKNOWN`；只有提供业务键、基数证据和批准记录后才能改为 `APPROVED`。已发布 `kb_release` 不原地修改。手动指标只在存在本地验证通过的计划、参数合同和可执行 SQL 模板并经用户发布后参与意图匹配。

### 手动指标管理

新指标管理只保留手动新增、查看、编辑和删除。新增时用户至少填写名称和自然语言描述，可选填人工确认的别名；描述应说明统计对象、时间口径、筛选、去重、分组、结果单位及缺失处理，无法确定的部分作为待补充项显示，不让模型猜。用户可先保存 `DRAFT`，再点击“一键 AI 生成 SQL”：系统检索当前发布的表结构 KB，把相关实体、字段、关系和示例交给模型，要求输出闭合逻辑计划及供审阅的 SQL 草稿。本地校验计划的字段/关系/粒度/参数语义，并由固定编译器生成真正可执行的参数化 SQL 模板；原始模型 SQL 只展示和留审计，不执行。发布前展示 SQL、所用表字段、适用条件、排除项和校验结果；有当前对话数据时可在隔离的只读连接预览，预览数据不能写入通用指标 SQL。

| 操作 | 输入与事务结果 | 查询侧影响 |
| --- | --- | --- |
| 新增 | 用户输入名称、自然语言描述；创建 `manual_metric` 与 `DRAFT` v1，系统不自动从文件或问答生成指标 | 草稿命中时提示尚不可执行 |
| 查看/列表 | 返回未删除指标的当前发布版、最新草稿、SQL 校验状态和更新时间；历史版本可单独查看 | 只读，不改变匹配候选 |
| 编辑 | 提交 `draft_revision`；草稿原地更新并清除旧 SQL/校验回执，已发布版则新建下一版本草稿 | 旧发布版继续按旧描述查询；新草稿不改变旧口径 |
| 删除 | 对 `manual_metric` 写 `deleted_at`，保留版本和历史 Run；重建同名指标须使用新 ID | 新请求不再检索该指标 |
| 一键生成 SQL | 对指定草稿启动 `metric_sql_graph`，生成 AI 提议及本地编译模板，记录缺口或进入 `VALIDATED` | 不自动发布、不自动执行 |
| 发布 | 用户确认本地编译模板及适用范围；事务内复验并将 `VALIDATED` 改为 `PUBLISHED`，切换 active 指针 | 后续新查询可优先命中该版本 |

指标版本状态为 `DRAFT -> SQL_DRAFT -> VALIDATED -> PUBLISHED`。AI 生成未通过本地验证时可保存 `SQL_DRAFT` 和具体缺口，只有 `VALIDATED` 可发布；重试生成会重新校验，不能仅改状态。编辑草稿以 `draft_revision` CAS 更新并递增，生成结果同时核对 revision、人工描述 hash、`last_generation_id` 和 KB hash，过期结果丢弃。名称、描述或影响口径的参数修改会产生待验证版本并使该版本的旧 SQL 失效；已发布版本不原地改写。发布事务重新验证计划、参数、KB 依赖、SQL 内容/hash 和回执，再更新 `manual_metric.active_version_id`，不能只检查列非空；数据库触发器禁止修改/删除已发布版本及指向未发布版本。旧版本继续供历史 Run 追溯。删除是软删除，新取数不再匹配，历史运行保留。KB 升级时对当前发布版本做兼容性检查；依赖字段或关系不可用则标记运行时 `SQL_STALE` 并要求重新生成/发布，不把旧 SQL 悄悄迁移到新 KB。

指标 SQL 模板不包含某个对话的实际 ID 或日期。执行时仅允许填充发布时声明的参数，并由服务端提供 `session_id` 与 `data_revision.id`；一次运行固定 `metricVersionId/sql_sha256/kbReleaseId/kbHash`。指标候选先按 `metricId` 折叠：默认以未删除指标的当前生效发布版本名称/描述作为可执行候选；同指标的最新草稿只提示未发布改动，不能用其新描述解释旧 SQL。新建未发布指标、用户显式指定草稿，或问题仅命中草稿新增描述时返回 `MATCH_UNAVAILABLE`。不同指标同名或语义相近仍需澄清。历史非生效版本和 Word 指标不进入新查询路由。

术语键包含实体 ID，所以“手术室”可同时指向首台、明细的来源列及退单的受控派生维度。“退单日期”同时映射来源“日期”和“退单时间”两个候选；没有上下文时应请求语义澄清，不能自行取其中一个。检索命中仅产生候选，不绕过字段权限与派生字段的使用前提。

每个固定 Excel 格式有独立的 `layout_version` 定义：支持的 Sheet 结构、精确表头及顺序、前置说明行、列到逻辑字段映射、必需列、枚举值、日期/时间解析规则和负例。当前三种标题分别包含“每日首台手术查询”“退单手术信息查询”“手术明细查询”；退单表头位于第 2 行，其余位于第 3 行。文件名用于退单手术室语义归属，不决定三类文件类型。新表头无法匹配已发布格式时拒绝入库并提示发布新格式版本。

## 5. 动态 SQL 的生成与执行

取数请求先按 `metricId` 折叠手动指标版本，以当前生效发布版本的名称精确匹配优先，再按其名称和自然语言描述做语义匹配；草稿仅用于识别不可执行的新定义。只有唯一、已发布且语义兼容的候选才能进入指标 SQL 分支；多个相近候选先澄清，明确无匹配才进入表结构 KB 动态 SQL 分支。命中指标但仍是草稿、SQL 缺失、过期或不支持本次条件时返回具体缺口，不能静默改用动态 SQL 冒充该指标。未命中时检索当前发布的 `kb_entity`、`kb_field`、`kb_term` 和 `kb_query_capability`，模型只返回闭合 JSON 计划，包含逻辑实体、投影、过滤、分组、聚合、排序、分页及可选的已批准关系 ID。计划中不含 SQL 片段、物理表名或任意函数；本地编译器负责生成动态 SQL。

本地校验器检查字段存在、类型、单位、粒度、聚合政策、关系基数、日期归属和数据质量。编译器从知识库中选择固定物理标识符，把用户值全部绑定为 SQL 参数；每个来源扫描先以服务端提供的 `session_id` 和 `data_revision.id` 限定来源，再进行连接与聚合。`COUNT(*)` 只能标注为“来源记录行数”。例如当前可明确回答“按日期列出退单表记录行数”，但不能把这个数称为去重后的退单手术台次。手术台次必须使用经批准的实体去重及实际状态政策；无法确定的关联或口径返回缺口，不生成近似 SQL。

上述退单行数示例可编译为以下查询。`revision_id` 与 `session_id` 均由服务端当前对话上下文注入，用户文本不能覆盖；日期条件若有也只能作为绑定参数加入。对话无数据时返回空结果及覆盖说明，不回退到其他对话。

```sql
SELECT r.record_date, COUNT(*) AS source_row_count
FROM cancellation_row AS r
JOIN data_sheet AS sh ON sh.id = r.sheet_id
JOIN data_source AS src ON src.id = sh.source_id
JOIN data_revision_source AS rs ON rs.source_id = src.id
JOIN data_revision AS rev ON rev.id = rs.revision_id
WHERE rev.id = :revision_id
  AND rev.session_id = :session_id
  AND rs.session_id = :session_id
  AND src.session_id = :session_id
  AND src.state = 'READY'
GROUP BY r.record_date
ORDER BY r.record_date
LIMIT :limit;
```

执行连接启用 `PRAGMA query_only=ON`，只开放编译器生成的 `SELECT`；使用 SQLite authorizer 拒绝写操作、`ATTACH`、非白名单表和函数，设置进度处理器、超时、最大返回行数及分页限制。`EXPLAIN QUERY PLAN` 可用于发现缺失索引和无界扫描，但不以查询计划替代业务语义校验。正式结果由本地精确计算核验，模型不接收患者明细或直接决定数字。

每次查询在现有 `run`/合同记录中固定 `session_id`、数据 revision/manifest hash、知识库 release/hash、结构化计划、SQL 模板 hash、绑定参数、算子版本、来源和质量问题摘要。普通诊断仅输出哈希与错误码，不输出敏感参数或结果明细。相同合同的重算可以复现；知识库升级不能改写历史运行。

## 6. 入库、备份和迁移

1. Worker 验证文件大小、真实格式、固定表头和格式版本；按 Sheet 暂存来源行及问题，逐行执行取消/预算检查。
2. 校验来源行数、哈希、重复文件和质量门禁。失败来源不得进入任何发布的 `data_revision`；崩溃后清理或继续 STAGING 来源。
3. 一个 SQLite 事务将来源设为 READY、写入新 revision 与完整来源清单并记录事件。首次导入建立 revision 1；补传或替换建立后继版本。移除文件也建立新版本，旧版本的来源仍保留供历史查询。
4. 数据库 schema 从当前 `meta.schema=1` 经编号迁移至 2；迁移前使用 SQLite backup API 备份，失败回滚。旧 Word 运行和检查点保留原合同，由旧读取路径查看；新运行使用三源合同。
5. 现有加密备份包含新的 SQLite 表和原文件 Blob。恢复后执行 `integrity_check`、`foreign_key_check`、来源 Blob 哈希、revision 清单及知识库 hash 校验。永久删除会话时先删除 revision 来源清单和问题记录，再删除 revision、标签、业务行、Sheet、来源及 data_space，并在确认无引用后清理 Blob。

## 7. 实施前必须确认的业务事实

| 问题 | 影响 |
| --- | --- |
| 当前样例的结构是否代表长期固定导出格式；字段允许为空的政策 | 将三种草稿格式合同发布为正式版本 |
| 是否存在跨三类文件稳定且唯一的手术业务键 | 决定能否批准跨表关联及首台/退单指标 |
| 系统生成“每日首台”结果的规则、是否只包含已执行记录 | 决定首台台次与准点率的统计口径 |
| 同一手术是否有多次退单、撤回、重排或重复导出 | 决定退单事件去重和关联基数 |
| 明细没有状态列时，哪些时间节点足以证明“已实施” | 决定实际台次的过滤与去重 |
| 只有 `HH:MM` 的时间在跨午夜时如何归日 | 决定时差、最晚时间和接台指标 |
| 文件名语义匹配器、阈值与负例是否经过校准；每份退单导出是否只属于一个手术室 | 决定自动归属比例、手动选择和按手术室统计的可靠性 |
| 各文件记录的时间区间是否完整、有无明确导出范围 | 决定零值与期间指标能否成立 |

在这些事实确认之前，表结构可以作为工程骨架，`kb_relation` 保持禁用；需要这些关系或未决口径的手动指标可保存自然语言草稿，但不能发布可执行 SQL。首个验收目标是：三份格式样例分别入库、当前对话查询隔离、补传后旧结果不变、指标命中先走已发布 SQL、无匹配走 KB 动态 SQL、跨表未批准关系被拒绝、每个结果可定位原文件行。
