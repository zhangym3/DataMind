## 4. 值得保留的设计

### 4.1 架构适合当前桌面工程

[方案 48–91 行](D:/DataMind/docs/backend-api-langgraph-plan.md:48)的 HTML/JS → QWebChannel → AppService → 工作进程 → 模型适配器/本地工具路径合理。单机版不必为了接口形式额外运行一个 HTTP 服务；HTTP 映射可以保留为未来扩展说明。

耗时任务放在独立进程，Qt 负责界面，业务事件屏蔽 LangGraph 内部结构，可以同时改善交互响应和版本兼容。

### 4.2 模型不能直接决定正式数字

[受控工具与职责](D:/DataMind/docs/backend-api-langgraph-plan.md:429)明确要求：模型理解、规划和解释，Python 按冻结合同计算。禁止执行模型临时生成的 Python/Shell，禁止反思节点改业务口径或直接改数字。这比扩大 Agent 自主权限更符合指标核算场景。

### 4.3 状态分层和保守发布正确

[业务约束](D:/DataMind/docs/backend-api-langgraph-plan.md:36)明确区分已导入、已识别、规则明确、数据满足、计算完成、可发布。歧义和不足只影响相关指标，跳过项不伪造 0，零可发布项不生成空白正式报告。这些应作为不可回退的产品约束。

### 4.4 版本追溯与幂等意识较成熟

[实体与版本](D:/DataMind/docs/backend-api-langgraph-plan.md:93)、[首问事务](D:/DataMind/docs/backend-api-langgraph-plan.md:254)、[检查点与提交日志](D:/DataMind/docs/backend-api-langgraph-plan.md:466)已考虑原文与规则双哈希、固定版本、消息/运行原子创建、节点重复执行和崩溃对账，没有把 checkpointer 错当成业务数据库或恰好执行一次的保证。

### 4.5 Skill 数量和职责克制

[四个功能 Skill](D:/DataMind/docs/backend-api-langgraph-plan.md:372)适合按业务能力组织实现。Ctrl+V、模型设置属于基础设施；文件路由适合固定子图，不需要再包装成自由调用 Skill 或增加自治 Agent。

### 4.6 在线配置考虑较充分

[模型设置](D:/DataMind/docs/backend-api-langgraph-plan.md:283)涵盖常用字段和能力测试、Key 不回显、系统凭据、目标服务源绑定、配置快照、轮换与停用。运行中不静默更换服务商，也是费用、数据目的地和结果追溯所需的明确边界。

## 5. 关键缺口及影响

优先级含义：**P0** 是相关核心链路开发前需要写清楚或用小原型证明；**P1** 是完整 MVP 验收/真实使用前需要完成；**P2** 可以后续扩展。并非所有 P0 都要同时开工。

### 5.1 P0：统一发送入口还不能完整表达“对话”

当前 [start_run](D:/DataMind/docs/backend-api-langgraph-plan.md:238)只有 `plan/analyze`，并依赖有效数据、已发布定义和模型配置。以下常见请求缺少明确路径：

- 只导入了 Excel：“有哪些字段？缺少什么？”
- 只导入了 Word：“指标说明完整吗？”
- 已有结果：“为什么这个指标被跳过？”“解释上一条的分母。”
- 没有数据：“怎么配置模型？”
- 已有多次分析：“刚才那个按科室再分组。”

如果全部当分析运行，会要求不必要的前置条件并消耗模型/计算资源；如果前端临时绕行，又会产生不一致的消息、锁定和来源规则。

需要补充“意图 → 所需输入 → 可访问的结果 → 是否计算 → 输出类型 → 是否触发锁定”的契约。业务发送仍可保持一个入口，由服务层路由，不必让前端先发消息再启动任务。

“按科室再分组”可以是规则允许的查询参数；“把阈值改为 25 分钟”可能修改已发布口径。两者必须有不同处理，不能由模型在旧版本名下悄悄改规则。

多轮记忆也需要固定 `sourceRunId/resultRef`、继承窗口/过滤/分组的规则、可继承字段白名单和上下文大小。结果歧义时不能任意选择最近一段文字，把旧条件误带到新问题。

### 5.2 P0：首问冻结与准备阶段需要明确的产品取舍

[当前规则](D:/DataMind/docs/backend-api-langgraph-plan.md:250)明确首个 PLAN 同样锁定文件和规则；锁定后需要通过普通“新建数据对话”重新选择数据和指标版本。这保证旧会话的基线与结果不被改写，但用户发现漏文件时需要重新开始准备。

不能在实现中自行把“首问锁定”变成“首次正式计算才锁定”。需要在产品规格中选定：

1. 保留严格首问锁定：把字段预览、准备检查和配置检查做成首问前的面板操作，并提前清楚提示 PLAN 会锁定。
2. 若希望自由预检查：明确修订哪些意图不构成首问锁定，并定义真正的冻结时点。

无论采用哪种规则，新建会话时都应展示当前未绑定的指标与需重新选择的数据，并明确没有原会话来源，避免用户误以为数据或口径已沿用。此处是交互代价评价，不是否定不可变快照。

### 5.3 P0：指标规则、算子和数据关联尚未形成可直接实现的正式规格

[MetricDefinition](D:/DataMind/docs/backend-api-langgraph-plan.md:103)和[计算工具](D:/DataMind/docs/backend-api-langgraph-plan.md:429)规定了方向；参考方案已经给出规则字段、JSON 示例和算子目录。这些不是从零缺失，但当前工程仍需要正式选取、版本化并补齐可执行契约，不能只在实现时“参考一下”。

至少需要确定：

- 统计对象、计数单位、手术事件键、过滤/排除条件、分子分母、分组与聚合层级。
- 日期归属、半开/闭区间、时区、跨午夜、阈值比较、单位转换与精度。
- 字段类型、算子输入输出类型、支持的组合、嵌套/基数限制和编译错误。
- 缺失、异常、零分母、真实重复、重叠导出及更正记录的处理。
- 关联键、关联基数、未匹配处理、冲突优先级、来源覆盖及关联后数量核验。
- 每个关键结论的原文证据，以及 schema/operator/dictionary 版本。

尤其要定义“映射已验证”的准入条件：可信字典、类型、上下文、唯一性、覆盖与冲突如何共同决定结果。模型建议、置信度或两次模型一致，不能单独构成验证依据。

例如同一患者两次手术，用住院号单值关联可能覆盖记录；一对多与多对多关联可能放大分子分母。方案已经指出这些风险，但尚缺能阻止它们发生的正式关联规格和可核算样例。

第一步应先验证少量受控指标的“Word → 规则 → 编译 → Python 计算 → 独立参考结果”，再扩展自然语言能力。不能用同一段计算逻辑给自己生成期望值。

### 5.4 P0：长文与多 Sheet 的覆盖策略不足

[准备流程](D:/DataMind/docs/backend-api-langgraph-plan.md:395)和资源预算已经提到扫描及覆盖，但没有充分规定：

- 长 Word 按何种结构切分，表格如何和标题、脚注、全局排除条件关联。
- 某指标引用另一章节定义时，如何把依赖一起送入提取/校验。
- 超出上下文后采用分层提取还是按指标检索，遗漏如何被发现。
- 多 Sheet、偏移表头、空表、合并单元格和扫描限额如何影响可用性结论。

如果只读前 N 段或抽几行，可能漏掉指标、例外和单位，却输出外观正常的结果。应先建立段落/表格/Sheet 的稳定定位和覆盖清单，再按指标及其依赖提取；每个已独立标识的指标都应进入已识别、明确跳过或技术失败等可追踪状态。

首次方案无需强制引入向量数据库。结构化切分、证据 ID、依赖提取和覆盖对账应优先于引入更多检索组件。

### 5.5 P0：全任务生命周期还缺少状态与动作的完整矩阵

[运行状态](D:/DataMind/docs/backend-api-langgraph-plan.md:264)、[错误码](D:/DataMind/docs/backend-api-langgraph-plan.md:334)和恢复原则较完整，但它们尚未覆盖附件、路由、定义解析、运行、导出的全部转换。

一个具体断点是：文件用途识别时服务超时，尚未创建 AnalysisRun。用户在设置中修好 Key 后，应该重试哪一个批次、是否沿用冻结的服务配置、如何避免重复创建定义草稿？当前只有运行级 recover 不够清楚，路由接口可重调也仍需明确授权动作和重试语义。

技术调用失败必须与语义 `UNKNOWN` 分开保存。网络断开不能永久变成“这份文件用途未知”。

需要一张状态转换表，至少规定对象、当前状态、允许动作、前置条件、新状态、事件、重试是否创建新修订，以及重启后的处理。任务调度还应明确：每会话串行之外，全局并发上限、工作进程所有权、租约到期/旧进程提交限制、关窗/退出行为、磁盘不足和卡死任务回收。

幂等、原子文件登记和提交对账已有良好原则，下一步是把它们落实到上述每种任务，而非再写一遍通用原则。

### 5.6 P0：出站最小化需要成为逐阶段可验证的载荷契约

[出站边界](D:/DataMind/docs/backend-api-langgraph-plan.md:560)已明确“不整包上传、统一脱敏、不能可靠处理就不发送”，[第 20 项验收](D:/DataMind/docs/backend-api-langgraph-plan.md:607)也要求抓取请求。这是优点；不足是目前缺少每个阶段的允许字段、实例和验证规则。

| 模型阶段 | 建议允许的最小载荷 | 重点约束 |
| --- | --- | --- |
| 文件角色识别 | 实际格式、结构画像、必要且已脱敏的标题/字段/片段、证据 ID | 不带原始路径；不能把任意样例行直接拼入提示词 |
| 指标规则提取 | 经检查的规则段落/表格及必要上下文、来源 ID | 文档正文也可能含身份信息；需保留全局限制和例外 |
| 问题规划 | 问题、可用指标目录、字段画像、明确查询参数、必要历史结果摘要 | 用户问题和自由文本同样经过出站检查 |
| 结果解释与复核 | 聚合结果、分子分母、覆盖/异常摘要、受控规则证据 | 默认不发送患者级成员集合；不让解释新增数值 |

若确需关联标识，优先在本地完成关联；确有出站需要时使用受控替代 ID，原始对应关系留在本地。脱敏失败应定位受影响阶段并停止相应发送，不能绕过组件或不加说明地丢失必要规则。

这里无需增加一次聊天中的泛化授权流程；需要把现有承诺变成真实请求可核验的技术约束。

### 5.7 P1：自动接入与定义发布之间的交互没有完全闭合

[现有规则](D:/DataMind/docs/backend-api-langgraph-plan.md:185)正确规定：识别为说明只创建草稿，粘贴不自动发布。仍需明确谁触发发布、哪些条件允许发布，以及用户不离开输入区能否完成它。

建议明确呈现：粘贴 Word → 显示识别角色与解析进度 → 展示识别指标数、合格候选与跳过摘要 → 显式“发布并用于此对话” → 固定版本绑定。已有版本或多份候选仍走明确选择，不能自动顶替。

这是定义配置管理动作，不应变成每个歧义指标都弹窗要求用户作语义选择。歧义项继续遵守自动跳过策略。

### 5.8 P1：离线确定性重算的承诺缺少明确入口

[降级设计](D:/DataMind/docs/backend-api-langgraph-plan.md:558)承诺无 Key、断网时仍可对已校验明确规则执行确定性重算；但 [start_run 前置校验](D:/DataMind/docs/backend-api-langgraph-plan.md:257)统一要求模型配置/凭据完整，主图还包含问题理解与 AI 复核。

这不一定意味着架构不能支持，而是当前接口没有明确表达例外。应说明离线重算使用哪个已冻结合同、是否复用既有审计/解释、哪些结果可发布、是否调用任何模型，以及对配置校验的区别。也可以收缩首版承诺为仅离线浏览历史，但这属于范围修订，不能由实现默默决定。

### 5.9 P1：验收清单尚未构成可执行的评价体系

[20 个场景](D:/DataMind/docs/backend-api-langgraph-plan.md:586)覆盖面较好，但“要测什么”和“怎样判定交付合格”仍有距离。需要独立标注的数据、预期值、预期跳过项、模型配置矩阵、验收责任和可复现执行方式。

建议验收目标如下；它们是未来拟定的门槛，不是已经取得的效果：

| 项目 | 建议的判定方式 |
| --- | --- |
| 数值正确性 | 必测独立样本中的计数、分子分母精确一致；小数按已声明精度/舍入规则比较 |
| 文件角色准入 | 必测负例不能错误进入数据计算或规则发布；分别统计误接入、误排除与 UNKNOWN |
| 规则提取覆盖 | 与独立人工指标清单核对，每项有提取/跳过/失败记录；不能只统计模型自行识别出的指标 |
| 合格项产出 | 明确且数据满足的必测项应生成；不能靠大量跳过把表面正确率提高 |
| 报告一致性 | 报告指标集合、值、单位、分子分母与最终白名单一致；无合格项无正式报告 |
| 故障恢复 | 在已列故障注入点重启后，无重复业务结果、历史覆盖或跨会话混用 |
| 在线载荷 | 测试夹具和实际出站请求满足逐阶段允许字段及脱敏规则 |
| 模型兼容 | 对承诺支持的服务商/模型，运行同一版本的结构化输出、错误与业务回归样例 |
| 性能与预算 | 先声明文件/Sheet/行数/指标数及目标机，再确定首结果、总耗时、内存和调用预算 |

有限样本通过不能证明任意输入的绝对正确，但没有这套基线就难以比较模型、调整提示词或判断回归。

### 5.10 P1/P2：首版范围、转换渲染与数据生命周期尚需定案

**领域范围：**建议首版以手术室指标验证完整链路；通用引擎保留扩展边界。若首版就要覆盖 UI 中的医院运营指标，需要额外提供对应定义、数据关系、算子和独立样本，而非直接复用手术分类字典。

**格式依赖：**`.doc/.xls`、公式重算、docx 页面验证和 PDF 需要真实转换/渲染能力。方案没有忽略这些问题，但尚未选定组件、打包方式、字体与无 Office 路径。应早做目标机验证，避免报告阶段才发现核心依赖不能交付。

**数据生命周期：**归档不是删除；按哈希共用的原件也不能被单会话删除破坏。需要定义删除/保留、暂存清理、引用计数、备份包含范围与恢复完整性。Key 存储已有设计，本地原件、数据库及备份还应有清楚的访问保护方案。

**升级与恢复：**诊断和完整备份界面可分期，但首次真实使用前至少需要可验证的一致性备份、关联文件恢复、迁移前备份和失败回退说明。仅数据库迁移版本号或检查点兼容声明不够。

## 6. UI 与交互评价

当前三栏结构适合“左侧会话与定义、中间分析、右侧输入与版本证据”的工作方式。结果采用 KPI + 明细 + 引用，也比纯长文本回答更适合复核。

从已保存的静态截图看，后续重点应放在这些位置：

1. 输入区附件卡片需要分别显示文件角色、处理状态和是否采用；不能用一个绿色勾同时表达已导入、可计算和已发布。
2. 将新增的模型配置入口做得明确；顶部“工作台已就绪”应与模型配置、网络可达、当前任务准备状态区分。
3. 结果区域应同时提供“已生成 N 项、已跳过 M 项、处理清单”，不让只看到部分漂亮 KPI 的用户误以为全部指标完成。
4. 当前版本、数据锁定及来源在主视图应可见，但技术哈希、内部阶段和调试细节放入详情，避免主流程堆满工程信息。
5. 低对比度次要文字、中文长文件名、宽表格、窗口缩小和系统缩放需要专项验证；目前未测量对比度或完成可访问性验收。
6. 补齐空态、处理中、部分成功、零可发布项、模型错误、取消中、恢复待处理等真实状态。静态成功页的视觉完成度不能替代异常交互完成度。

## 7. 建议的实施与补齐顺序

### 第一段：先证明规则和数字可靠

- 确定首版领域、支持格式和明确的算子集合。
- 选取少量具有代表性的指标，包含计数、比例、时间边界和必要关联，不只选择最简单的展示项。
- 固化规则 Schema、映射/关联契约和独立人工结果；验证原文证据和跳过条件。
- 使用 `.xlsx + .docx` 先打通样本，旧格式依赖另行验证后开放。

### 第二段：把准备、发送和追问做成完整流程

- 补齐意图、锁定时点、历史引用和定义发布流程。
- 实现粘贴/选择/拖放统一接入及固定路由子图。
- 模型设置保留常见服务商预设与自定义接口，但首轮只承诺已经验证的少量适配组合，不把预设列表当兼容证明。
- 先让结构化结果和证据完整，再扩展图表及多种导出格式。

### 第三段：完成恢复、报告和桌面验收

- 在全任务状态机下验证取消、崩溃、重启、重试和提交对账。
- 确定 docx 生成与页面验证路径，再开放具备实际转换能力的 PDF。
- 在未安装 Python 的目标机验证 Qt WebEngine、工作进程、中文路径、凭据、转换器、字体及备份恢复。
- 按独立样本、负例和故障注入门槛验收后，再扩大领域与格式范围。

不建议此时增加更多 Skill、自治 Agent 或通用插件系统。当前收益最高的投入是明确规则契约、可核算样本、完整任务状态和真实业务交互。

## 8. 开工与交付判断

**可以开始：**小范围规则/计算原型、独立样本核算、桌面桥接契约和模型出站适配验证。

**应先补规格再全面开发：**对话意图、首问冻结边界、规则/算子 Schema、映射/关联验证、长文覆盖、路由失败恢复及逐阶段出站载荷。

**不能据此认定已经具备：**任意指标自动理解能力、真实数据计算正确性、目标机性能、所有预设模型兼容性或生产交付就绪。

建议保留当前主架构，用“粘贴文件 → 明确采用 → 发布并绑定规则 → PLAN/分析 → 可核算结果与跳过清单 → 验证报告 → 重启可追溯”的一条实际链路检验方案，再扩展功能数量。
